# Architecture rules
- Match detail availability uses the selected live partner package capped by any local allocation, refreshing while open; legacy match counters must not block available packages.
- Import Tripadvisor reviews plus the newest Airbnb and Viator reviews (public listing pages, each site falling back to its previous reviews) through a fixed-source, authenticated weekly Firecrawl job with deterministic parsing and service-only snapshot writes; the home carousel reads the last successful public snapshot without scraping on visits or loading third-party widgets.
- Review carousel visibility/count settings use a validated admin-only endpoint and the shared review selector; unconnected Google imports remain disabled, and public Google snippets must never be represented as a complete newest feed.
- Public match inventory uses a bounded RPC exposing only availability fields; raw local overrides and administrative metadata remain admin-only.
- Public blog ratings use an aggregate-only RPC; raw feedback and visitor identifiers are admin-only, with local submission memory and database uniqueness preventing repeated ratings.
- Public sales inserts must start unpaid, uncancelled, unarchived and without delivery/payment-link fields; payment workers and verified admins retain privileged writes.
- Anonymous visit records are written by the existing service-side tracking function, not direct table inserts; public catalogue reads honor active/visible flags and short-link administration requires the admin role.
- Share English/Portuguese calendar snippets through `src/lib/maracanaCalendarSeo.js` and preserve the generated calendar HTML during SPA fallback; this prevents loading-state and build-step metadata drift.
- Schedule pending Stripe reconciliation from server-created checkout session IDs in a service-only capability queue; derive the 15-minute deadline from sale creation, stop scheduling after drain, and reuse `sync-stripe` for existing paid-sale side effects.
- Share recorded reservation amount formatting through `supabase/functions/_shared/reservationPresentation.ts`, re-exported for the frontend; email and admin details must format stored denominations without exchange-rate conversion.
- Route all paid-sale confirmations through the database-triggered `process-paid-sale-email` worker, preserving Resend templates; store per-audience acceptance and stable provider idempotency keys, and arm retries only while pending deliveries exist so partner inserts and Stripe updates share one low-cost path.
- Derive generic game page and static route metadata through `src/lib/matchSeo.js`; sharing registered teams, venue and Rio-local date prevents incorrect stadium labels and generic published titles.
- Share fixture status and event detail derivation through `src/lib/matchEventStatus.ts`, consumed by the general schema generator and landing builders; this keeps approved timing and home-team rules consistent without changing stored match data.
- Select match carousel photos from the existing site gallery through `getMatchGallery` in `src/lib/matchImages.ts`; this keeps stadium selection testable without extra requests or duplicated image storage.
- Select each stadium's featured match video through `getMatchFeaturedVideo` in `src/lib/matchImages.ts`; Nilton Santos games use their own YouTube Short, so per-stadium videos stay testable in one place.
- Share football reservation identification between sales UI and email functions through `supabase/functions/_shared/footballReservation.ts`, re-exported from `src/lib/footballReservation.ts`, so presentation stays consistent without changing stored booking or payment data.
- Keep Vasco–Boca landing metadata and event-offer generation in `src/lib/vascoBocaLanding.ts`, using the existing matches query for live data; this shares build-time metadata without adding AI calls or a separate booking flow.- Keep Flamengo–Estudiantes landing metadata and event-offer generation in `src/lib/flamengoEstudiantesLanding.ts`, using the existing matches query for live data; mirrors the Vasco–Boca landing pattern without a separate booking flow.
- Store weekly-refreshed fallback exchange rates in `site_settings` key `fallback_exchange_rates` via `refresh-fallback-rates`; site and checkout use it only when the live rate API fails, keeping fallbacks aligned without per-request polling.
- Public checkout prices are re-derived server-side from the tour catalogue or partner match packages and bound to the customer's unpaid reservation; checkout confirmation reads/writes reservations only via the Stripe session id, so URLs with sale ids alone expose nothing.
- Weekly Reddit ticket-question alerts run in `reddit-ticket-questions` (Firecrawl search+scrape, max 5 posts, one low-effort AI reply each with fixed-template fallback, owner email via Resend); it never posts to Reddit, avoiding spam bans and AI cost.
